TREC 2025 Million LLMs Track

A plain-English, source-backed guide to the task, data, features, submissions, results, and evaluation caveats for the Million LLMs Track at the 2025 Text REtrieval Conference.

What This Track Asked

The track tested whether a system can route a user question to the LLM ID that is most likely to be an expert for that question. The submitted system ranked model IDs, not web pages and not generated answers.

1,131candidate LLM IDs in the official pool
14,950discovery queries reported by the overview paper
342development queries with relevance labels
50NIST-authored test questions described in the overview
19official automatic submitted runs
6participating groups in the official run list
Big caveat: the final official evaluation was much smaller and noisier than the original design. The overview reports ground-truth answers for 37 of 50 test questions, but only 16 questions had at least one relevant model answer. Relevance was judged by GPT-5-as-judge rather than the originally planned pooled human assessment.

Plain-English Problem

Imagine a company has many specialized assistants. One is good at law, another at local history, another at chemistry, and so on. A user asks a question. Before spending money asking every assistant, the system must predict which assistant should answer. TREC 2025 made this a benchmark: rank the best model IDs for each query using only the released data.

The word "million" is aspirational. In 2025 the benchmark used 1,131 simulated expert LLM IDs. They were not 1,131 separately trained foundation models. They were shared LLM-based systems whose apparent expertise came from different retrieval collections.

This matters because the task is closer to expert retrieval or model routing than to ordinary document retrieval. Systems exploit evidence from previous query-answer behavior, response confidence, embeddings, metadata, and topic/domain profiles.

1. User queryA natural-language or keyword-like information need.
2. Candidate LLM IDsEach ID behaves like a specialist backed by a document cluster.
3. Submitted rankingTeams return a TREC run file ranking model IDs.
4. Hidden answersModel answers are compared to reference answers.
5. MetricsnDCG@10 and MRR reward putting good experts near the top.

Glossary

TREC
The Text REtrieval Conference, a long-running evaluation forum run by NIST.
Run
One official submission: a ranked list of LLM IDs for each test query.
qrels
Relevance labels. Here they say how expert a model answer appears for a query.
nDCG@10
A top-10 ranking metric. Higher is better when highly relevant items appear near the top.
MRR
Mean Reciprocal Rank. It focuses on how early the first relevant result appears.
BM25 / RM3
Classic search methods. BM25 matches query terms; RM3 expands the query using pseudo-relevance feedback.
Profile
A saved summary of one candidate ID's historical work, built before the new query arrives.
Embedding
A list of numbers representing one item, such as a query or response, in a learned similarity space.
Centroid
A representative center of a group of similar embeddings. It is a compact topic summary, not a correctness label.

How the simulated expert LLMs were created

The overview describes a large document collection being clustered into topical groups. Each LLM ID corresponds to a cluster-backed expert RAG-style behavior. A single global BM25 index retrieved up to 2,000 documents per query; for each cluster, up to the top three documents found in that global pool could condition the shared LLM's answer. If a cluster had no documents in the global pool, a default template was used.

This construction gives each ID a different evidence environment, so the benchmark can ask which ID is likely to answer a new question well. It also means the track evaluates routing among simulated experts, not comparisons among unrelated commercial LLMs.

Example test questions from the public topic file

Examples include local-history and long-tail factual questions such as "What is the history of the Rumsey Mansion in Joppatowne?", "What famous woman allegedly visited Mount Athos?", and a detailed question about a first-edition scientific mistake in Larry Niven's Ringworld. These are intentionally difficult for general LLMs and often require niche source grounding.

Features and Modeling Ideas

Each item below is a clue that a ranking system can use. Two terms are easy to confuse: a profile is a saved résumé for one candidate built from many past records, while an embedding is a list of meaning coordinates for one item. The pictures below unpack both terms before the feature catalog.

Start here: neither idea is magic. A profile stores evidence we already observed about one candidate. An embedding gives the system a numerical way to compare the meaning of text.

Why response-level evidence mattered

GenAIus found that indexing individual historical responses and aggregating scores back to LLM IDs was stronger than treating each LLM as one giant profile document. That makes intuitive sense: a single model profile can blur many domains together, while a response-level index can match a new query to similar past query-answer behavior.

SRCB: pseudo-label the answer matrix, then train a neural scorer

SRCB's system is easiest to understand as synthetic supervision. It first creates labels for unlabeled discovery answers, then trains a model that scores every LLM ID for a new query.

rank 1neurallabel-risk
1. Training rowsCreate query-response rows for the discovery matrix: about 15k queries by 1,131 candidate LLM answers.
2. Judge labelsUse Quicksort pairwise judging: compare candidate answers to anchors, recursively split better/equal/worse groups, and form a per-query ranking.
3. Backup labelsAdd Qwen3-Reranker-8B query-response scores and embedding similarity to either a generated reference answer or the query.
4. EncoderFreeze a strong pretrained encoder. The practical winner reported was Qwen3-Embedding-8B; DeBERTa-v3 was another baseline.
5. Prediction headTrain ranking, classification, or regression heads. Reported losses included BCE, ListNet, cross entropy, focal loss, and BCE-style regression.
6. Test-time rankingEncode the test query, produce one score for each of the 1,131 LLM IDs, optionally ensemble variants, then sort by score.
  1. Implementation recipe: begin with one label source, preferably reranker or embedding similarity, before implementing expensive Quicksort judging.
  2. Data shape: a supervised table of query, LLM ID, answer text, pseudo-label, and optional label-source metadata.
  3. Validation: use the 342 development queries to choose label source, head type, top-percentile threshold, and ensemble weights.

Why it worked: it turned a routing problem with sparse human labels into a large supervised ranking problem.

Main failure mode: the model may learn the judge's style preferences instead of real expertise.

UDInfo: estimate quality near similar past queries

UDInfo's best method is a hybrid router. It asks: for queries similar to this one, which LLMs were judged good, and which LLMs are strong in this query's domain cluster?

rank 2hybrid routerdebuggable
1. Embed queriesEncode discovery and test queries with BAAI/bge-large-en, then L2-normalize so cosine similarity can be computed efficiently.
2. Weak labelsUse an external judge, reported as olmo2-13b, to grade each discovery query-LLM answer as 0, 1, or 2.
3. Local evidenceBuild a FAISS index over discovery query embeddings. For a test query, retrieve K = 100 nearest discovery queries.
4. Local scoreFor each LLM, compute a similarity-weighted average of its weak labels over those neighbors, then smooth with its global prior using alpha = 0.9.
5. Domain scoreCluster discovery queries into Kc = 40 groups. Precompute each LLM's average judged quality in each cluster.
6. Final scoreAssign the test query to the closest cluster and mix local and domain scores with lambda = 0.5.
  1. Implementation recipe: build the query FAISS index first, then add cluster priors once local-neighbor scoring works.
  2. Useful baseline: Method 1 stores K_m = 10 answer centroids per LLM and combines broad centroid similarity with per-LLM FAISS refinement.
  3. Debug handle: inspect nearest training queries and the assigned cluster when a routed LLM looks surprising.

Why it worked: it keeps three interpretable quantities separate: nearby examples, global model quality, and domain quality.

Main failure mode: bad weak labels poison both local and cluster estimates.

GenAIus: retrieve historical answers and aggregate back to LLM IDs

GenAIus is the most reproducible strong baseline. It treats each past answer as retrievable evidence, then gives credit to the LLM that produced the matched answer.

rank 3easy baselineBM25/RM3
1. Start corpusBegin with roughly 16.9M discovery responses, each tied to a query and producing LLM ID.
2. Filter failuresRemove exact and patterned failures such as "No result found"; the first filter left about 2.83M responses.
3. Filter refusalsRemove low-information refusal phrases; the stricter response set was about 1.24M responses.
4. Build indexesCompare profile, question, and response indexes. The response index was strongest: one document per historical answer.
5. RetrieveRun BM25 with RM3 pseudo-relevance feedback. For response runs, retrieve up to 1,000 response documents.
6. AggregateUse SumScore: add each retrieved document's score to its producing LLM, then sort LLM totals.
  1. Implementation recipe: store fields for query text, response text, LLM ID, and filter reason; keep filtered and extra-filtered indexes separate.
  2. Scoring choice: SumScore outperformed simple Vote because Vote creates more ties and ignores retrieval confidence.
  3. Optional rerank: rerank retrieved response documents with naver-splade-v3 before aggregating back to LLM IDs.

Why it worked: matching a new query to individual past answers is more precise than matching it to one giant LLM profile.

Main failure mode: lexical retrieval misses semantic matches unless RM3/reranking or embeddings are added.

indelab: compare neural routing with engineered ensembles

indelab submitted both a neural dual-encoder idea and a stronger non-neural ensemble. The useful lesson is how to represent both the query and the model as scoring features.

rank 12ensembledual encoder
1. Weak examplesCombine dev qrels with weak discovery labels based on response length: over 50 characters becomes relevant, otherwise non-relevant.
2. Neural query towerProcess 384-d query embeddings with 4-head attention, reshape 384 to 96 x 4 to 384, then dense layers to 128-d.
3. Neural LLM towerLearn LLM embeddings with a 1,131 to 256 lookup, then dense layers 256 to 512 to 384 to 256 to 128.
4. Neural scoreCompute cosine similarity between 128-d query and LLM representations; ensemble the five best folds by dev nDCG@10.
5. Feature ensembleFit Bradley-Terry skill, random forest with query/model/profile features, and a LightGBM meta-ranker over about 17 features.
6. Final rankingUse the ensemble/meta-ranker scores to rank all LLM IDs for each test query.
  1. Implementation recipe: reproduce the non-neural ensemble first; it is easier to inspect than the dual encoder.
  2. Neural gap: the official appendix does not specify the exact training loss, so choose and document pairwise, contrastive, or regression loss.
  3. Validation: use 10-fold dev-query validation and avoid letting weak length labels dominate real qrels.

Why it helped: it explores whether LLM IDs can be embedded like retrievable experts.

Main failure mode: response length is a crude label and can reward verbosity instead of correctness.

uvairlab: use confidence metadata as learning-to-rank features

UvA IRLab used token log probabilities as a compact model-behavior signal. The final feature row is small: query vector, LLM ID, and two confidence statistics.

rank 13LightGBMconfidence risk
1. Query vectorEncode each query with Sentence-BERT all-MiniLM-L6-v2, yielding a 384-dimensional vector.
2. LLM ID featureConvert each LLM ID to a scalar integer, such as llm_0032 to 32, so LightGBM can split on it.
3. Logprob summaryFor each discovery response, compute average token log-likelihood as a confidence score.
4. Model statsFor each LLM, keep its top 1% confidence responses and compute mean and standard deviation.
5. Train rankerTrain LightGBM LambdaRank with learning rate 0.05, max leaves 31, early stopping 50, and about 1,130 rounds.
6. Build 387-d rowsFor each test query, create 1,131 feature rows: 384 query dims plus LLM ID, mean, and std; sort predictions.
  1. Implementation recipe: precompute per-LLM confidence summaries once; inference only embeds the query and joins the two stats.
  2. Labels: convert average log-likelihood into grades: below -2.0 is 0, -2.0 to -1.0 is 1, above -1.0 is 2.
  3. Extension: add 100 query clusters and per-cluster confidence/refusal/length features to make the model domain-aware.

Why it is attractive: the feature table is small, fast, and easy to train.

Main failure mode: confident answers can still be wrong, especially for hallucinated or over-general responses.

paulphys: build behavioral profiles for each LLM

paulphys tried to summarize each LLM's behavior in a 64-dimensional profile, then match query descriptors to those profiles with LambdaMART.

rank 19profilesdiagnostic
1. Sample responsesUse 50% of discovery responses; the paper reports that sampling more did not improve profile quality.
2. Embed behaviorEncode sampled responses with Qwen3-Embedding-8B and compute semantic centroids, dispersion, and similarity statistics.
3. Handcraft categoriesAssign domain labels such as science, medicine, law, history, and task labels such as explanation, comparison, and factual.
4. Build 64-d profileCombine domain/task expertise, response metrics, lexical diversity, structure, semantic descriptors, and query-response overlap.
5. Pair featuresFor each query-LLM pair, concatenate query descriptors, the LLM profile, domain/task matches, and interaction products.
6. LambdaMARTTrain LightGBM LambdaMART with rank_xendcg; train on top 200 LLMs per dev query and rank all 1,131 at inference.
  1. Implementation recipe: use this to make interpretable diagnostics alongside a stronger router, not as the first production ranker.
  2. Feature audit: check which profile dimensions dominate; handcrafted domain labels can overfit the dev distribution.
  3. Debug handle: show profile-domain matches to explain why a model was routed to a query.

Why it is useful: behavioral profiles expose what the router believes each LLM is good at.

Main failure mode: profile summaries can be too coarse for long-tail questions, which likely contributed to the weak official score.

What Each Team Submitted

These summaries combine the official run descriptions, the track overview, and participant papers.

SRCB: LLM-assisted label construction and neural ranking

SRCB treated the track as a supervised ranking problem with no real labels for the discovery set. Their implementation recipe is: manufacture pseudo-labels for every query-model answer, train an efficient per-query model scorer, then ensemble the best variants.

SRCB implementation flow

1. Materialize examplesFor every discovery query, keep one row per LLM answer: query text, LLM ID, answer text, and any existing metadata. This creates a large pseudo-supervised table even before true labels exist.
2. Generate label variantsCreate several target columns: Quicksort pairwise-judge rank, Qwen3-Reranker-8B score, embedding similarity to a generated answer, embedding similarity to the query, and a combined label.
3. Train small headsFreeze the encoder and swap lightweight heads: one score per LLM for ranking, 3-way classification for top groups, or sigmoid regression for continuous pseudo-labels.
4. Validate label sourceUse dev qrels to choose the label source, top-percentile threshold, loss function, and ensemble rule. The key check is whether labels predict expertise, not just polished answer style.

Inputs and preprocessing

  • Use the discovery matrix: roughly 15k queries by 1,131 candidate LLM responses.
  • For each query, keep the candidate response text for every LLM. The labels are constructed over responses, but the submitted ranker ultimately returns LLM IDs.
  • Use the development qrels only for model selection and hyperparameter tuning.

Pseudo-label construction

  1. Quicksort labels: for each query, pick an anchor response, ask a strong LLM whether each other response is better or worse than the anchor, split into good/anchor/bad groups, and recurse until a full ranking is produced. Assign ties when responses are identical or judged equivalent.
  2. Reranker labels: score each query-response pair with Qwen3-Reranker-8B and convert the scores into a ranking.
  3. Embedding-similarity labels: either generate a strong reference answer and compare each candidate response to it, or compare the response directly to the query. Use a strong embedding model for cosine similarity.
  4. Combination labels: ensemble the above label sources. Their paper reports Quicksort and Combination as the strongest label-construction families.

Ranking model

  • Freeze a pretrained encoder for efficiency, then train lightweight task heads. They compared DeBERTa-v3-base, Qwen3-Embedding-8B, and Qwen3-32B; Qwen3-Embedding-8B was the practical winner.
  • Try three formulations: ranking with one output score per LLM, classification with a 3-class head per LLM, and regression with a sigmoid score per LLM.
  • Losses tested included BCE and ListNet for ranking, cross entropy and focal loss for classification, and BCE-style regression.
  • Convert continuous pseudo-labels into top-percentile categories when using classification; for regression, zeroing labels outside the top x% improved reported development performance.

Inference flow

  1. Encode the test query.
  2. Produce 1,131 scores, one per candidate LLM ID.
  3. Optionally ensemble several trained variants by voting or score aggregation.
  4. Sort LLM IDs by final score and emit the TREC run.

Implement first: start with Qwen3-Embedding-8B plus Combination or Quicksort labels and a regression/ranking head. Avoid: trusting pseudo-labels without validation; this system can learn the judge model's style preferences as much as true expertise.

UDInfo: profile embeddings, weak LLM labels, and neural routers

UDInfo is the cleanest source for implementation recipes because the paper describes five concrete routing methods. Their best official run was Method 2, a hybrid query-space model with weak LLM labels, kNN evidence, and domain clusters.

UDInfo Method 2 implementation flow

1. Build query spaceEmbed all discovery queries with BAAI/bge-large-en, L2-normalize, and build a FAISS index. At inference retrieve the nearest K = 100 discovery queries.
2. Build weak-label tableUse olmo2-13b-style judging to assign each query-LLM answer a grade in {0, 1, 2}. Also compute each LLM's global average grade as a prior.
3. Score local neighborsFor each candidate LLM, take a similarity-weighted average of its grades over the 100 neighbor queries, then smooth that local score with the global prior using alpha = 0.9.
4. Add domain cluster scoreCluster discovery queries into Kc = 40 groups, store each LLM's average grade per cluster, assign the test query to the closest cluster, and mix local/domain scores with lambda = 0.5.

Method 1: hierarchical answer-profile router

  1. Embed all discovery answers with BAAI/bge-large-en; L2-normalize vectors so cosine similarity is a dot product.
  2. For each LLM, run k-means over its answer embeddings with K_m = 10. Store centroids as that model's broad expertise profile.
  3. Build one FAISS index per LLM over its normalized answer embeddings.
  4. At inference, embed the query. Compute broad score as max similarity to the LLM's centroids.
  5. For refinement, retrieve K = 10 nearest answer embeddings from each LLM's FAISS index and average their similarities.
  6. Combine broad and refined scores with a mixing parameter. UDInfo reports alpha = 0.2, chosen on development data.

Method 2: hybrid weak-label query router

  1. Use an external LLM judge, reported as olmo2-13b, to assign each discovery query-LLM answer a grade in {0, 1, 2}.
  2. Embed discovery queries with BAAI/bge-large-en and L2-normalize.
  3. Build a FAISS index over query embeddings. At inference, retrieve the top K = 100 nearest discovery queries.
  4. For each LLM, compute a similarity-weighted average of its weak labels over those neighbors.
  5. Smooth that local estimate with the LLM's global prior using alpha = 0.9.
  6. Cluster discovery queries into K_c = 40 k-means clusters. Precompute each LLM's average judged quality in each cluster and smooth with the global prior.
  7. Assign the test query to its closest cluster and combine local and domain scores with lambda = 0.5.

Other UDInfo baselines

  • Method 3: answer-centroid profile only. For each LLM, store 10 answer centroids and score a query by max centroid similarity. This is Method 1 without the FAISS refinement stage.
  • Method 4: shallow MLP classifier. Weak-label each query, select the best judged LLM as the class label, embed the query, and train a PyTorch MLP with hidden sizes 512 and 256, ReLU activations, Adam at 1e-3, and 20 epochs.
  • Method 5: deeper MLP router, same basic target as Method 4 but with higher capacity.

Implement first: Method 2. It has the best official UDInfo score and directly separates local evidence, global prior, and domain cluster expertise. Avoid: a pure MLP router as the first implementation; it is less interpretable and underperformed the hybrid method.

GenAIus: classic retrieval over profiles, questions, and responses

GenAIus is the most reproducible starting point if you want a strong non-neural baseline. They reframe model routing as expert search: retrieve historical evidence, then aggregate evidence back to LLM IDs.

GenAIus response-retrieval flow

1. Filter response corpusStart from about 16.9M query-response pairs. Remove no-result strings, then remove refusal/low-information patterns; the strict set reported about 1.24M responses.
2. Choose index grainBuild three candidates: one giant profile document per LLM, one document per discovery question, and one document per historical response. The response index was strongest.
3. Retrieve evidenceRun BM25 with RM3 query expansion against the response index. Retrieve the top 1,000 response documents for each test query, optionally reranking with naver-splade-v3.
4. Aggregate to LLM IDsFor SumScore, add each retrieved document's retrieval score to the accumulator for the LLM that produced it. Sort accumulators; fill missing LLMs with a low default score if needed.

Filtering

  • Start with all discovery query-response pairs: about 16.9M responses.
  • Initial filter: remove responses equal to or containing obvious failure strings such as No result found. This left about 2.83M responses.
  • Additional filter: remove refusal/low-information patterns such as I don't have knowledge about or I don't have enough information. This left about 1.24M responses.
  • Keep the mapping from every indexed document to the LLM ID that produced it.

Three indexes to build

  1. LLM profile index: one document per LLM, created by concatenating that LLM's historical query-response pairs. The official profile run ranked these documents with BM25 and submitted the top 100 LLMs; RM3 was tested for this profile setup but reduced performance and was not used in the final profile run.
  2. Question index: one document per discovery query. Associate each query document with the LLMs that survived filtering for that query. Retrieve top 100 query documents, then vote or sum scores into LLM IDs.
  3. Response index: one document per historical response, usually query plus response text. Retrieve top 1,000 response documents, then aggregate by LLM ID. This was their strongest family.

Scoring and aggregation

  • Use BM25 for first-stage retrieval and RM3 for pseudo-relevance feedback query expansion.
  • Use Vote if each retrieved document should count equally for its LLM.
  • Use SumScore if each retrieved document contributes its retrieval score. GenAIus preferred SumScore because Vote created more ties.
  • Optional: rerank the top response documents with naver-splade-v3, then aggregate reranked scores.

Inference flow

  1. Run the test query against the response index with BM25/RM3.
  2. Retrieve top 1,000 response documents.
  3. For each document, add its score to the producing LLM's accumulator.
  4. Sort LLM IDs by accumulated score. Fill missing IDs with a default low score if a full ranking is required.

Implement first: response-level BM25/RM3 with SumScore over extra-filtered responses. Avoid: starting with one giant profile document per LLM; it is simple but loses query-specific evidence.

indelab: neural dual encoder and non-neural ensemble

indelab has two implementation tracks in the official appendices. The non-neural ensemble was stronger officially; the neural dual encoder is useful as a blueprint for query-model representation learning.

indelab two-track flow

1. Build weak supervisionCombine dev qrels with discovery examples labeled by a response-length heuristic: answers longer than 50 characters become positive, shorter answers become negative.
2. Neural scorerMap 384-d query embeddings through attention and dense layers to 128-d. Map learned LLM IDs through dense layers to 128-d. Score by cosine similarity.
3. Non-neural scorerFit Bradley-Terry global skill from pairwise response-quality wins, then train a 150-tree random forest and a LightGBM meta-ranker over about 17 engineered features.
4. Ensemble selectionUse 10-fold dev-query validation, keep the five best neural folds by nDCG@10, and compare them against the feature ensemble before final ranking.

Neural dual-encoder run

  • Training data: about 4.45M examples, combining development qrels and weakly labeled discovery examples.
  • Weak discovery labels: if a response length is greater than 50 characters, assign relevance 1.0; otherwise assign 0.0. This is crude but cheap.
  • Use 10-fold cross-validation over development queries. Train with 90% of dev queries plus all weak discovery examples, validate on the held-out 10%, and ensemble the five best folds by validation nDCG@10.
  • Query tower: process 384-dimensional query embeddings with 4-head attention, reshape through 384 -> 96 x 4 -> 384, then dense layers 384 -> 256 -> 192 -> 128.
  • LLM tower: learned LLM embeddings 1131 -> 256, then dense layers 256 -> 512 -> 384 -> 256 -> 128.
  • Score each query-LLM pair by cosine similarity between the 128-dimensional query and LLM representations. Average scores across the five fold models.

The official description does not specify the exact training loss, so an implementation should make that choice explicit: pairwise ranking loss, contrastive loss, or regression to qrels are all plausible, but not documented as indelab's exact choice.

Non-neural ensemble run

  1. Bradley-Terry skill model: create pairwise wins/losses between LLMs using heuristic response quality signals such as length, structure, reasoning markers, and examples. Fit a global skill value per LLM.
  2. Enhanced random forest: train roughly 150 trees on about 250k examples. Features include TF-IDF query vectors, LLM embeddings, query-complexity metrics, and discovery-profile features.
  3. LightGBM meta-ranker: combine about 17 meta-features, including judge-like scores, Bradley-Terry skill, query characteristics, and cross-component interactions.

Implement first: the non-neural ensemble if you want robustness and interpretability. Avoid: relying on response length as a strong quality label; it is a weak bootstrap signal and can reward verbosity.

uvairlab: LightGBM over confidence and query features

UvA IRLab built a compact learning-to-rank system around response confidence. The key idea is to use token-level log probabilities as cheap pseudo-supervision and as model-level capability features.

uvairlab confidence-ranking flow

1. Precompute confidenceFor every discovery response, average token log-likelihood. Convert those values into pseudo labels: below -2 is 0, -2 to -1 is 1, above -1 is 2.
2. Summarize each LLMFor each LLM, keep the top 1% highest-confidence responses. Compute the mean and standard deviation of that subset as global capability and consistency features.
3. Build 387-d rowsConcatenate the 384-d all-MiniLM-L6-v2 query embedding, scalar LLM ID, top-1% confidence mean, and top-1% confidence standard deviation.
4. Train LambdaRankTrain LightGBM LambdaRank for NDCG@1/5/10 with learning rate 0.05, max leaves 31, early stopping 50, and about 1,130 rounds.

Official LightGBM feature vector

  • Encode the query with Sentence-BERT all-MiniLM-L6-v2, producing a 384-dimensional query vector.
  • Convert each LLM ID to a scalar integer, such as llm_0032 -> 32. LightGBM can split on this feature even though the numeric order is arbitrary.
  • For each discovery query-LLM response, compute average token log-likelihood.
  • For each LLM, take its top 1% highest average-loglikelihood responses. Compute the mean and standard deviation over that subset as global capability and consistency features.
  • Concatenate [query_embedding_384, llm_id, global_mean, global_std] for a 387-dimensional feature vector.

Labels and training

  • Convert average log-likelihood into pseudo-relevance grades: below -2.0 is 0, between -2.0 and -1.0 is 1, and above -1.0 is 2.
  • Train LightGBM LambdaRank to optimize NDCG at 1, 5, and 10.
  • Reported configuration: learning rate 0.05, maximum leaves 31, early stopping after 50 rounds, final rounds 1130.

Inference flow

  1. Embed the incoming query once with SBERT.
  2. For every candidate LLM, join the query vector with that LLM's ID and precomputed global confidence statistics.
  3. Score all 1,131 feature rows with LightGBM.
  4. Sort LLM IDs by predicted score.

Useful extension

The paper reports a post-submission topic-aware extension: cluster discovery queries into 100 SBERT k-means clusters, compute per-cluster LLM confidence mean/std, refusal rate, mean response length, cluster size, and distances to the three nearest centroids. This expands the vector to about 408 dimensions and makes the router more domain-sensitive.

Implement first: LightGBM with query embedding, LLM ID, and top-1% logprob mean/std. Avoid: interpreting confidence as correctness; the paper explicitly warns that confident hallucinations remain possible.

paulphys: behavioral profiles and LambdaMART

The paulphys run is a compact behavioral-profile design: build one feature vector per LLM summarizing how it behaves, then train LambdaMART to match query descriptors to those profiles.

paulphys behavioral-profile flow

1. Sample and embedSample 50% of discovery responses and embed with Qwen3-Embedding-8B. Compute semantic centroids, dispersion, and response similarity statistics per LLM.
2. Build behavioral profileCreate a 64-d vector covering handcrafted domains/tasks, response length/logprob metrics, lexical diversity, structure, query-response overlap, and semantic summaries.
3. Create pair featuresFor each query-LLM pair, concatenate query descriptors, the LLM profile, domain/task match indicators, and elementwise interaction products.
4. Rank with LambdaMARTTrain LightGBM LambdaMART using rank_xendcg on the top 200 LLMs per dev query, then score all 1,131 LLMs during inference.

Profile construction

  • Sample 50% of discovery responses; the paper reports that using more than half did not improve profile quality.
  • Embed responses with Qwen3-Embedding-8B.
  • For each LLM, compute a 64-dimensional behavioral profile covering domain expertise, task strengths, quality indicators, semantic descriptors, and statistical summaries.
  • Domain labels are handcrafted: technology, science, medicine, law, business, education, arts, sports, politics, history.
  • Task labels are handcrafted: explanation, comparison, analysis, instruction, creative, technical, factual.

Feature groups

  • Response metrics: token and character counts, log probabilities, punctuation ratios.
  • Lexical diversity: type-token ratio and repetition rates.
  • Structure: sentence counts, code/list usage, formatting, uppercase and digit frequency.
  • Query-response interaction: Jaccard similarity and keyword overlap.
  • Semantic embedding features: centroids, dispersion, and similarity statistics from Qwen3-Embedding-8B.

Ranking setup

  1. For each incoming query, compute query descriptors such as length and type-token ratio.
  2. Infer query domain and task category with keyword matching.
  3. For every query-LLM pair, concatenate query descriptors, the LLM behavioral profile, domain/task match features, and elementwise products between query labels and profile scores.
  4. Aggregate domain/task interactions with simple statistics such as mean, standard deviation, and maximum.
  5. Train LightGBM LambdaMART with the rank_xendcg objective. The paper trained on the top 200 LLMs per development query and ranked all 1,131 at inference.

Implement first: use this as an interpretable feature baseline, not as your only production router. Avoid: relying on handcrafted domain/task categories alone; the official run ranked last, likely from overfitting and test distribution shift.

How to Interpret the Findings

The 2025 track is valuable as a first benchmark and literature snapshot, but it should not be read as a settled leaderboard for production model routing.

Evaluation was small

Only 16 test questions had at least one relevant answer, so official scores are high-variance and hard to generalize.

Judging changed

The original plan involved pooled human assessment. The actual evaluation used GPT-5-as-judge against reference answers.

Experts were simulated

The candidate LLM IDs were shared-model RAG-style experts with different retrieval clusters, not independently trained models.

Counts differ across sources

The overview says 14,950 discovery queries, while some participant papers report 14,940. The public final topic files have 48 rows, though the overview discusses 50 test questions.

Development gains did not always transfer

Several papers report strong development results that did not translate into official test scores, suggesting distribution shift and overfitting risk.

Weak labels can encode bias

LLM-as-judge or reranker-generated labels can help, but they may reward answer style or judge-model preferences rather than true expertise.

Practical recommendations for a 2026-style system
  1. Start with response-level retrieval over historical query-answer pairs, then aggregate to model IDs.
  2. Add answer filtering for refusals, empty responses, and low-evidence answers.
  3. Use embeddings and topic/domain profiles as complementary signals, not replacements for historical evidence.
  4. Treat log probabilities as confidence features, not as proof of correctness.
  5. If using LLM judges for weak labels, keep judge identity, prompt, and calibration visible in the methodology.
  6. Validate on held-out long-tail queries and report uncertainty, because leaderboard order is fragile when the judged set is small.
